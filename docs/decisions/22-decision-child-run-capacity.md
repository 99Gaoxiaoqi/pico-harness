# 决策记录 22：子代理真实执行容量的 turn 域 FIFO 信号量（2026-08-18）

> 提交：`a38b82eb`。实现见 `src/tools/child-run-limiter.ts`，测试见
> `tests/integration/child-run-limiter.test.ts`。

## 背景与实证

**前车之鉴：candidate 选举的 OOM 风暴。** 2026-08-17，8GB 内存的 HDP 云桌面在
14 秒内堆积起约 20 个 candidate 候选进程导致内存耗尽。那次事故的主体是
runtime-host 的候选选举层，不是子���理委派——但它揭示的病根与本决策要治的
缺口同构：**每一层配额都属于某个独立作用域，没有任何一层看着进程总量**。

子代理委派当时是同病的未爆区域：

- pico 的配额全部是 session 级：3 委派批次 / 3 批内并发 / 2 嵌套深度。
- daemon 是多 session 集中架构：N 个 session 各自的"3×3×2"在同一 Node 进程
  里叠加，对进程无界。选举层不补这个缺口，下一个 OOM 就可能从这里来。

**行业调研（三家对比）**：

| 产品        | 并发模型                                            | 对本问题的启示                                 |
| ----------- | --------------------------------------------------- | ---------------------------------------------- |
| pico（旧）  | 全 session 级 3/3/2，进程级无闸                     | 缺口所在                                       |
| Claude Code | 一进程一会话天然隔离 + `isConcurrencySafe` 二元分类 | 隔离靠进程边界，pico 的 daemon 架构不具备      |
| maka        | 双层：准入 5/turn + 执行容量 32 的 FIFO 信号量      | 准入与真实执行容量是独立边界；满则排队优于拒绝 |

## 决策

新增 `ChildRunLimiter`，挂在**最窄的 spawn 能力**上（子代理真实执行的外层），
让所有调用方共享同一份真实执行预算：

1. **容量**：默认 32（对齐 maka 的经验值；`PICO_CHILD_RUN_CAPACITY`
   可覆盖），构造时读取一次。
2. **满则 FIFO 排队**：不拒绝、不丢弃；���队中被取消则干净出队拒绝。
   排队优于拒绝是 maka 验证过的取舍——拒绝会把"稍后再试"的协调成本
   转嫁给模型，排队只需背压。
3. **域 = turn**：每个 turn 换新实例、旧实例 close。语义：
   - 每 turn 满血准入——容量按 turn 配速，不被历史占用拖累；
   - 跨 turn 仍在跑的子代理把名额归还给旧实例，**不占新 turn 预算**——
     防止多轮委派的会话被累积的在飞子代理永久堵死；
   - turn 结束仍在排队的等待者按 "permit scope ended" 拒绝——饱和背压，
     让模型在下一 turn 重新决策，而不是挂着一个永不满足的等待。

## 放弃的备选及理由

- **继续在 session 级加/调配额**：OOM 的根因就是"每 session 独立配额无人看
  总量"，在同一层调数字治标不治本。
- **进程级拒绝式限流（满则报错）**：丢任务不可接受（探索类子代理失败会
  误导主 Agent 的判断）；FIFO 排队以延迟换完整性。
- **daemon 全局单一限流器（跨 turn 持久容量池）**：跨 turn 累积的在飞子代理
  会让长会话逐渐饿死新 turn，且"容量何时归还"与 turn 生命周期脱钩后无法
  判定等待者该不该继续等。

## 已知接受的代价

1. **turn 结束仍在排队的等待者被拒绝**（饱和背压）——调用方需要把
   "permit scope ended" 当作可重试的软失败处理。
2. **容量是进程内状态**——daemon 重启即重置（与 spawn 能力本身同生命周期，
   不构成第二事实源，见治理文档 P2 的 ADR 问句）。

## 复评条件

- 出现跨 turn 的长时委派产品需求（如后台多阶段任务）时，重估"域 = turn"
  的选择——届时可能需要显式的跨 turn 容量租约而非 turn 域满血模型。
