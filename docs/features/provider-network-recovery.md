# 模型连接失败与有限重试

2026-09-23，鹈鹕骑车长程任务的失败排查与修复记录。

## 根因

任务里的命令审批已经通过，工具也已执行完成；失败发生在下一次模型请求。独立 Node fetch 请求 OpenCode 的模型列表时，同样复现了约 5 秒后的 `ECONNRESET`，后续请求又成功，说明瞬时 TLS 建连失败与审批无关。

AI SDK 会将 Node 的 `TypeError: fetch failed` 解包为携带底层 cause 的 `APICallError`。Pico 在脱敏包装后保留了安全的 transportCode，但 Runtime 原来的分类没有利用该字段，导致本应可恢复的连接失败只尝试一次就结束任务。

## 修复边界

- 对 `request_failed`，仅在尚无 HTTP 状态、尚未观察到响应头时，识别六种安全传输码：`ECONNRESET`、`EAI_AGAIN`、`ETIMEDOUT`、`UND_ERR_CONNECT_TIMEOUT`、`UND_ERR_HEADERS_TIMEOUT`、`UND_ERR_SOCKET`。
- 每次逻辑调用默认最多 10 次总尝试（含首次），与 Maka 固定基线一致。指数退避基数从 1 秒起，基数在 32 秒封顶，附加 0–25% 抖动，单次实际等待最多 40 秒；退避可取消。
- 已执行工具和已经通过的审批不重放；仅重新发送尚未成功的模型请求。
- 取消、未知错误、无错误码的脱敏错误、永久性连接配置错误，以及已经收到响应的传输错误，不进入此次新增的传输恢复分支。
- 每次物理尝试仍独立记账，共享逻辑调用身份并递增 retryAttempt。错误原因原文、请求正文和凭证不进入诊断输出。

## 长生成暴露的第二个问题

安装网络修复后，真实任务两次在一次重试后成功继续。随后另一次逻辑调用在网络重试建立连接后，持续生成绘图代码，却分别在 119,998ms、119,994ms 被默认硬期限取消。两次都已收到 HTTP 200 和首个输出。因此这不是审批等待，也不是再次建连失败。

普通 `generateStream` 未显式传入 `timeoutMs` 时，现改为 120 秒无有效进展超时。非空正文、推理、工具参数增量及工具调用/结果会续期；原始心跳、空增量不会无限延长请求。显式 `timeoutMs`、父级取消与非流式调用保留硬期限。

已经产生语义输出后发生超时，会返回不可重试的 `incomplete_stream`，保留部分展示，不自动重跑这次响应。没有输出的超时仍保留现有的一次超时重试上限。Maka 对全部 SDK chunk 续期，并对封闭推理提供专门恢复；Pico 此处采用有效进展续期与保守终止，未移植该特殊恢复。

最初仅修复分类时保留了 3 次总尝试。追加流式修复后，实机成功产出三个版本及 final PNG，但收尾请求连续三次约 5 秒的 TLS 建连失败，最终耗尽。依据该实测，默认预算升级为 Maka 的 10 次总尝试及更长退避，而非通过手动重复执行工具维持任务。

## 确定性验收

6 个 Provider 集成测试文件共 16 项通过，覆盖三个现有 Provider 的 SDK 主路径、错误脱敏、六种安全传输码恢复、显式 3 次预算耗尽、默认 10 次预算耗尽、取消与响应后错误不进入新增恢复分支，以及完整 AgentRuntime 中“审批一次 → 编辑一次 → 下一请求 TLS 失败 → 请求恢复”的持久化结果。

新增流式集成测试在旧基线证明失败，修复后三协议持续输出跨越 180 秒虚拟时间成功；覆盖文本、推理、工具参数续期，纯心跳和静默超时，显式硬期限、父级取消，以及有输出后超时只保留一次 physical attempt、不重新生成。

默认预算测试同样在旧基线证明失败；修复后连续三次 TLS 失败能在第四次恢复，持续失败恰好十次停止，并校验退避上下界和等待中的立即取消。

通过 `build:packages`、根目录及桌面 TypeScript 检查、架构检查、相关 ESLint/Prettier 与桌面打包。网络修复首次打包遭遇下载网络失败，第二次完成；追加流式修复后的最终打包也通过产物校验。
