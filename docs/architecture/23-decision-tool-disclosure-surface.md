## 背景与实证

工具披露要解决的问题：工具数量增长后，全部塞进 `tools` 数组会稀释模型注意力、
撑爆请求；披露过少又让模型"不知道自己有这个能力"。旧系统（详见 13 号文档）
是五套披露机制的组合，其中模型主动检索走 `search_tools` 的**单工具级子串
匹配**。三家对比（2026-08-17 调研）暴露出旧系统三个结构性短板：

| 短板 | 旧系统行为 | 后果 |
|---|---|---|
| **不持久** | 披露状态是内存态 | 会话恢复/子代理继承/断线重连后，已披露的工具集丢失，模型"失忆"重复检索 |
| **下轮生效** | 披露结果下一 turn 才进入 tools 数组 | 模型本 turn 检索到工具却不能立刻用，多一轮空转 |
| **匹配精度** | 子串 OR 匹配 | `edit` 匹配到不相关的长名工具；语义近邻（write/update）召回不稳 |

三家对比给出的优先级判断：**持久化 > 同轮生效 > 匹配精度**——前两者是结构性
缺陷（丢状态、多空转），后者是质量问题（可由模型重试兜底）。

## 决策

1. **surface 目录**：工具按组声明披露面（名称、描述、激活条件），取代散落在
   多处的五套机制——披露的定义单点化。
2. **load_tools 组级激活**：模型检索命中时以**组**为单位激活（枚举式），而非
   单工具子串匹配——组是模型心智的自然单位（"文件编辑组"而非 edit_file 一个）。
3. **durable 重播**：披露状态作为 durable 事件落盘，会话恢复时重播——补上
   持久化短板。
4. **TF-IDF 两步协议**：检索匹配从子串改为 TF-IDF 相关性排序——补匹配精度
   短板，对齐行业两步协议（先相关度召回、命中才进 tools 数组）的成熟做法。

## 放弃的备选及理由

- **修补旧五套机制**（在 search_tools 上加同义词表/权重）：治标——不持久、
  下轮生效两个结构性短板无法在旧架构内解决，越修越复杂。
- **全量披露**（工具全进 tools 数组）：工具数继续增长后注意力稀释与 token
  成本不可控；三家无一采用全量。
- **只做持久化不动匹配**（按优先级只修第一短板）：durable 重播落地后组级
  枚举与 TF-IDF 的边际改动小，一次收口避免二次重构。

## 已知接受的代价

1. **deferred 工具永不进 tools 数组**——模型必须先检索才能用，首次使用多一步；
   换取的是 tools 数组恒定小体积与 prompt cache 友好。

## 实现教训（非代价，后续同类改动的约束）

- 新增事件 kind 必须同步 `assertRuntimeEvent`（两轮对抗审查抓出的暗坑：漏了
  会静默吞错掩盖死代码）——这条已沉淀为测试约束。

## 复评条件

- 出现单组工具数显著增长（组内枚举本身变重）时，评估组内再分层；
- TF-IDF 实测召回不达预期时，评估嵌入检索（当前刻意保持零嵌入依赖）。
